# 文档中心（docs）

> 单一事实来源：每类信息只活在一个文档里。本文件是唯一入口，找文档先看这里。

## 分支协作规则

| 角色 | 职责 |
|---|---|
| AI 助手（研发） | **只在 `feature/*` 分支上修改、提交、推送**，禁止直接提交 main |
| 项目所有者（你） | 审查 feature 分支后**自行合并到 main**，合并节奏自己掌握 |

- 合并方式建议：`git checkout main && git merge feature/mvp-core`（历史线性时为快进）
- main 上发现问题：开新 issue 式记录（`quality/测试记录.md` 或 reviews），修复仍在 feature 分支进行

## 目录结构

```
docs/
├── README.md            ← 你在这里：导航 + 文档规范
├── product/             【产品域】PM 维护——回答"做什么、做成什么样"
│   ├── PRD.md               产品需求文档（v1.0 定稿）
│   └── 需求规格Spec.md       EARS 句式规格（v0.2 定稿）
├── tech/                【技术域】研发维护——回答"怎么实现"
│   ├── TRD.md               技术方案（v0.1）
│   ├── API契约.md           接口契约（v0.2，前后端并行依据）
│   └── adr/                 架构决策记录（为什么这么做）
├── quality/             【质量域】QA 维护——回答"是否符合规格"
│   ├── 自测清单.md           提测门禁（约 40% 已勾）
│   └── 测试记录.md           bug 跟踪与回归
├── pm/                  【项目管理域】全员共写——回答"何时、欠了什么债"
│   ├── 计划与排期.md         里程碑 + 风险登记 + 站会记录
│   └── 技术债务.md           8 笔在册，带偿还触发条件

    └── 2026-10-03-PRD评审.md
```

**仓库根目录还有**：[CHANGELOG.md](../CHANGELOG.md)（面向使用者的变更日志）、[README.md](../README.md)（运行手册）。

## 文档规范（人人遵守）

### 1. 目录按域划分，新文档必须归位

| 你要写的东西 | 放哪 |
|---|---|
| 需求、功能规格、验收标准 | `product/` |
| 技术方案、接口、架构决策 | `tech/`（重大决策另建 `tech/adr/NNN-*.md`） |
| 测试用例、bug 记录、回归报告 | `quality/` |
| 排期、风险、技术债务、复盘 | `pm/` |
| 某次评审的结论 | `reviews/`（命名：`YYYY-MM-DD-主题.md`） |

**禁止**在 `docs/` 根目录直接放文件（本 README 除外）——这是迭代不乱的关键。

### 2. 命名规范

- 文件名用中文名或英文均可，**不带序号前缀**（归属目录已经表达了类别，序号会在重排序时制造无谓 diff）
- 评审记录、周报等**带日期**的文档：`YYYY-MM-DD-主题.md`，永不覆盖旧文件
- ADR：`NNN-短标题.md`，NNN 三位递增，**用过的不复用**

### 3. 文档生命周期

```
草稿(draft) → 评审中(in-review) → 定稿(final) → 归档(archived)
                                   ↓ 被新版替代
                              移入 archive/ 或标注"已废弃，见 vX.Y"
```

- 文档头部必须有：版本、日期、状态、维护者
- 定稿文档修改必须升版本号并在 CHANGELOG 留痕
- 评审记录只追加，永不修改——错误的决议也留着，那是决策痕迹

### 4. 冲突裁决顺序

PRD（为什么做）→ Spec（精确做成什么样）→ TRD（怎么实现）。三者有冲突，**以 Spec 为准**——它最精确、可验收。

### 5. 迭代期的新增流程（v2 起）

1. 新需求先在 `pm/计划与排期.md` 的需求池登记，不直接写 PRD
2. v2 启动时从需求池挑选 → 新建 `product/PRD-v2.md`（v1 移入 `product/archive/`）
3. 每个版本归档自己的文档副本，历史可回溯
